# 证据链、阈值与时间来源

一条素材的判定不是「猜」，是**一串带权重的证据**，最高分那条赢。`guicang explain <路径>`
把整串证据打出来——判断归错了的时候，先看这段输出，别急着改代码。

## 拍摄类型：完整优先级

`classify.classify_shot()` 从上到下扫，第一条命中的直接返回（后面不再看）。

| # | 规则 | 严格条件 | 权重 | 证据 rule 名 |
|---|---|---|---|---|
| 1 | FPV 字样 | 路径命中 `FPV` / `Avata` | 0.90 | `path:fpv` |
| 2 | 延时字样 | `延时` / `timelapse` / `hyperlapse` / `time-lapse` | 0.88 | `path:timelapse` |
| 3 | 航拍字样 | `航拍` / `无人机` / `aerial` / `无人机` | 0.86 | `path:aerial` |
| 4 | 地拍字样 | `地拍` / `地面` / `手持` / `ground` | 0.84 | `path:ground` |
| 5 | 无人机机型 | `FC\d{4}`、mavic、`mini \d`、`air \d`、phantom、inspire、matrice、neo、御、精灵、悟 | 0.84 | `camera:drone` |
| 6 | 相对高度 | `alt_kind == "relative"`（DJI 的 `rel_alt`）且 `> 8` 米 | 0.80 | `telemetry:altitude` |
| 7 | 地面机型 | osmo、pocket、action、ronin、iphone、canon、nikon、sony、fuji、lumix、leica、eos、ilce、a7x、dsc-、x-t | 0.80 | `camera:ground` |
| 8 | 手机文件名 | 文件名以 `IMG_` / `PXL_` / `VID_` / `ScreenShot` / `wx_camera_` / `mmexport` 开头 | 0.80 | `path:phone_prefix` |
| 9 | 运动相机文件名 | `GOPR` / `GP01` / `GX01` / `HERO` 开头 | 0.80 | `path:action_prefix` |
| 10 | 相机文件名 | `MVI_` / `MOV_` / `DSC_` / `_DSC` / `DSCN` / `P1xxxxxx` 开头 | 0.78 | `path:camera_prefix` |
| 11 | DJI 文件名无机型 | 文件名以 `DJI_数字` 开头但读不到机型号 | 0.55 | `path:dji_prefix` |
| 12 | 什么都没有 | — | 0.50 / 照片 0.45 | `default` |

**为什么要按文件名前缀猜（8–10 号）？** 手机上拍的照片常常没有 EXIF 机型，云端（归云那条路）
连 EXIF 都读不到。但手机和相机拍出来的默认文件名是固定的：`IMG_`/`PXL_` 是手机、`GOPR` 是
GoPro、`MVI_`/`DSC_` 是相机——**没有一个是无人机**（无人机用 `DJI_`）。所以这条证据站得住，
而且它把「明明能判却进了待定」的那批素材救了回来。读得到机型时按机型走，这条只在机型缺失
或机型不认识时生效。

**为什么路径压过机型？** 天天自己建的目录名是他**当时的判断**（「延时」「航拍」「地拍」），
比机器认机型更可信。所以路径规则永远在最前面。

**为什么 11 号规则重要？** DJI 素材删过 EXIF 的很多，机型读不出来但文件名还是 `DJI_0001.MP4`。
按「地拍 0.50」归是错的；按「航拍 0.55」也不会对——所以落在 0.55，进待定，让人来看。
这就是「诚实」的实现方式：不确定 = 待定，不是 = 猜一个。

**8 米悬崖。** `rel_alt` 是相对起飞点的高度。飞 5 米的航拍镜头（贴地跟拍）会被判成地拍，这是
故意的——低空镜头和地拍在剪辑上几乎等价。用户不同意就 `review --set --shot 航拍`。

**只看相对高度，不看海拔。** EXIF 里的 `GPSAltitude` 是海拔（郑州地面就 100 米），拿它判航拍会全错。
所以 `Probe` 上多了一个 `alt_kind`：只有 `relative`（DJI 遥测的 `rel_alt`）才参与判定，
EXIF 的海拔一律标 `absolute`、不参战。视频的坐标来自 MP4 的 ISO6709、高度来自 `.SRT` 时，
两件事各按各的来源走，不会因为坐标来自另一个来源就把高度丢掉。

## 区域：优先级与置信度

`classify.classify_region()`：

1. **GPS**（EXIF 或 MP4 的 `location.ISO6709` 或 `.SRT` 遥测）→ 找最近地点。
   - 在半径内：`confidence = 0.95 - 0.33 * (dist / radius)`，圆心 0.95、边缘 0.62。
   - 半径外但最近点 < 3km：留一条 `gps:outside` 证据（提示你半径给小了），区域仍判为未识别。
2. **路径里的地名**：`confidence = min(0.88, 0.66 + 0.03 * len(别名))`——别名越长越可信，
   `开封古城` 比 `开封` 可信。
3. 都没有 → `None`（→ 待定）。

别名匹配按**最长优先**：同时有「开封」和「开封古城」，路径写了「开封古城」就记后者。

`classify_region()` 现在返回的是**地点对象**（`Place`），不是地名——省、市、园区区域都是这个对象的属性，
认到地点之后由 `decide()` 一起带下来。人工钉住地点之后，`settle_place()` 会按名字反查清单，
把省/市补上，并重新检查园区区域还缺不缺。

## 园区区域：只在路径里找

`classify.classify_area(place, rel_path)`：

- 只在 `place.areas` 里列过的名字与别名中找，**最长匹配胜出**，命中即 `0.90`（证据 `path:area`）。
- 不猜、不从坐标推。园区里有几块是人的事，机器只负责对号入座。
- 地点配了 `areas` 但这条对不上 → `needs_review`，原因写清「对不上是哪一块」。这是设计上的硬要求：
  宁可让一条待定，也不要把它悄悄扔到地点根目录里，让以后找不到。

## 机型层：多才分

`build_layout()` 统计「同一地点 + 同一园区区域 + 同一天 + 同一拍摄类型」下的机型集合：

- 集合里 **≥2 种机型** → 这一组落位时多一层机型目录（`…\地拍\Canon EOS R5\`）。
- 只有 1 种（或读不到机型）→ 不分层，文件直接躺在拍摄类型目录下。
- 读不到机型的那条在需要分层时进 `未知机型\`，不是扔掉。

`[layout] camera = false` 可以把这一层彻底关掉（就算撞机型也不分）。

## 活动与届次

`classify.classify_activity()`：

- 路径里出现活动名或别名 → 基础置信 0.75 起，别名越长越高（同区域公式）。
- **有届次**（`第39届`、`第十一届`）→ 记 `edition = "第39届"`（统一成阿拉伯数字）。
- **无届次** → 用拍摄年份当那一段，并把置信 `-0.04`（说明这是一次性的，不是重复举办的）。
- `activity_conf >= 0.7` 才把 `branch` 从 `region` 翻成 `activity`。

`editions` 字段目前只是预留：未来的用法是「一个素材没写届次，按年份查那一年的活动别名」。
现在不参与判定，写不写都行。

## 时间来源：优先级

| 来源 | 权重 | 从哪读 |
|---|---|---|
| EXIF `DateTimeOriginal` | 0.95 | JPEG/TIFF/CR2 的 APP1 IFD |
| MP4 `mvhd` 创建时间 | 0.90 | moov box，按盒子跳读，不吞整段视频 |
| `.SRT` 里带日期的时间戳 | 0.85 | 第一行 `00:00:00,000 --> ...` 上方的日期（部分机型有） |
| 文件名里的日期 | 0.72 | `2024-05-18`、`20240518`、`2024_05_18_093015` |
| 文件修改时间 | 0.35 | `st_mtime` |

**mtime 为什么只有 0.35？** 拷过一轮盘的素材 mtime 全是拷的那天。天天这种到处拷素材的，
mtime 基本没用，所以它只在完全没别的线索时兜底。

**MP4 时间不做时区换算。** mvhd 里写的就是相机本地墙钟时间；按 UTC 解再转 +08:00 会把
清晨 5 点搬到下午 1 点。这条踩过一次，测试 `test_exif_probe.py` 里钉死了。

**机型不重复 make。** `make="DJI"`、`model="DJI Mavic 3 Pro"` → 显示 `DJI Mavic 3 Pro` 而不是
`DJI DJI Mavic 3 Pro`（`model.camera_name()`）。

## 旁车文件（sidecar）

`.srt` `.lrf` `.thm` `.xmp` `.aae` `.lrv` `.dop` `.xml` 不单独入库，按「同目录同名」挂到主文件上：

- `.srt`：取 `rel_alt`（判航拍）、`latitude/longitude`（判区域）、`abs_alt`、`focal_len`。
- `.xmp`：目前只占位，不解析（Lightroom 里的标注自有它的价值，但格式太散，先不做）。
- 找不到主文件（比如单独一个 `.srt`）→ 计入 `skipped`，不报错、不静默吞。

## 置信度阈值一览

| 常量 | 值 | 含义 |
|---|---|---|
| `AUTO_THRESHOLD` | 0.75 | 低于它 → 待定 |
| `ACTIVITY_THRESHOLD` | 0.70 | 高于它 → 走活动枝 |
| 半径圆心 | 0.95 | GPS 正中的把握 |
| 半径边缘 | 0.62 | 卡在半径线上（→ 待定，合理） |
| `path:dji_prefix` | 0.55 | 无人机但读不到机型（→ 待定） |
| `default` | 0.50 | 啥都不知道（→ 待定） |
| mtime 时间 | 0.35 | 时间也不可信，但总比 `未知时间` 强 |

## 排查「为什么归错了」

```
$ guicang explain "2024-05-19 泡泡塘森林溪谷/露营区/IMG_8842.JPG"
2024-05-19 泡泡塘森林溪谷/露营区/IMG_8842.JPG
  拍摄类型 地拍（0.80）
    · camera = Canon EOS R5（0.80）
  区域      河南 → 郑州 → 泡泡塘森林溪谷 → 露营区（0.95）
    · gps: 距 泡泡塘森林溪谷 0.12km（0.95）
    · path:area 露营区（0.90）
  落位 区域/郑州/泡泡塘森林溪谷/露营区/2024-05-19/地拍/Canon EOS R5/IMG_8842.JPG
  状态 auto
```

读法：

1. **先看拍摄类型那条最高分**。如果写的是 `default`，说明这台机器什么都没认出来——查机型是否在表里。
2. **再看区域**。如果是 `path:` 那说明没 GPS（或 GPS 在半径外）。
3. 如果是 `manual`，那就是人钉的，机器不背锅。
4. 想改就 `review --set`，别改代码。

`scan` 的计数也会告诉你真相：

| 计数 | 含义 |
|---|---|
| `新增` | 索引里没有的 |
| `更新` | 判定变了（改了配置、钉了人工判定都会触发） |
| `未变` | 读数没变、判定也没变，**但判定重算过**（复用索引里的读数，不重读文件） |
| `待定` | 本轮结束后仍待定的条数（累计值，不是本轮新增） |
| `跳过` | 旁车、隐藏文件、配置目录、树目录 |
| `错误` | 读文件失败（权限、损坏），出现在这里要修 |

**「未变」也会重算判定。** 这条是刻意设计的：改了 `places.toml` 或 `review --set` 之后，
不需要 `--force` 也能生效；`--force` 只用于「文件内容可能变了但大小和 mtime 没变」这种极端情况。
